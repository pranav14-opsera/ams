# Retention Policy Enforcement & Cold Storage Tiering (WO-049)

## Architecture

- **`RetentionPolicyService`/`RetentionPolicyController`** — `GET/POST/PUT /api/v1/audit/retention-policies`: per-tenant, per-data-category (`audit_logs`, `execution_traces`, `usage_metrics`) retention configuration, with platform-wide min/max bounds and a 30-day grace period on any shortening.
- **`ColdStorageTieringService`** — daily job: archives `audit_events` partitions older than 90 days to cold storage (NDJSON), verifies the archive's checksum, then physically detaches and drops the live Postgres partition.
- **`RetentionPurgeService`** — daily job: deletes a tiered archive once every tenant's own retention period for that data has elapsed.
- **Query federation** — `GET /api/v1/audit/logs?cold_storage=true` merges matching rows from tiered archives back into the normal query response.

## The central architectural tension: per-tenant policy vs. physically shared storage

`audit_events` is partitioned by **time only** (migration 005: `PARTITION BY RANGE (occurred_at)`, monthly partitions), not by tenant — a single partition holds every tenant's rows for that month. Retention policy, by contrast, is naturally per-tenant (a compliance officer configures *their own* org's retention). This WO reconciles the two as follows, rather than silently picking one and ignoring the mismatch:

- **Tiering (90-day threshold) is NOT tenant-configurable.** It is a fixed, platform-wide operational threshold (per the AC's own text: "partitions older than 90 days"), independent of any tenant's retention_days. A partition is archived-then-dropped from hot storage once its data is entirely more than 90 days old, regardless of what any tenant's retention policy says — the data isn't gone, it's just moved to cold storage, so no tenant's retention guarantee is affected by tiering itself.
- **Purging (physical deletion) IS gated by retention policy**, but since one archive covers every tenant's rows for that period, it can only be deleted once **every tenant's** own retention period for that period has elapsed — never merely the tenant with the shortest policy. `RetentionPurgeService.maxEffectiveRetentionDaysAcrossTenants()` computes the **maximum** effective retention across all tenants (falling back to each category's platform default for tenants with no override) and only purges once `periodEnd + maxRetentionDays < now()`. This means a tenant's data is never purged *before* their own policy allows, at the cost of occasionally retaining another tenant's already-expired data a little longer within the same shared archive — the safe, conservative direction to err in for a compliance feature.
- A real production system at this scale would likely partition `audit_events` by `(tenant_id, occurred_at)` compound sharding, or store retention-differentiated tenants in materially different tables/buckets, to avoid this shared-blast-radius tradeoff entirely — a bigger structural change than this WO's scope, flagged here as a genuine follow-up worth prioritizing if per-tenant retention divergence becomes common in practice.

## RLS forces a per-tenant loop for platform-level operations

`audit_events` (and its partitions — PostgreSQL RLS policies on a partitioned parent apply identically to every partition) is RLS-protected per tenant, and `ams_app` (WO-004's least-privilege application role) never bypasses RLS — there is no "read across all tenants in one query" available to the app layer at all, by design. Both `ColdStorageTieringService` (to archive a full partition) and `RetentionPurgeService` (to compute the cross-tenant maximum retention) therefore loop over every tenant (from the `tenants` table itself, which has no RLS — same structural exception as every other WO that's needed this), opening a fresh `set_config('app.current_tenant', ...)`-scoped connection per tenant. This is the same idiom WO-043/047/048 already established for any platform-level, outside-a-single-tenant's-request operation; it is not a new pattern.

## No real S3/Parquet/Athena in this sandbox

Same documented gap as every prior WO touching cloud storage (`AUDIT_EXPORT_QUERY_API.md`'s `ExportStoragePort`/`LocalFilesystemExportStorageService` precedent, mirrored exactly here as `ColdStorageAdapterPort`/`LocalFilesystemColdStorageService`): no AWS credentials, no reachable S3 endpoint, and — new to this WO — no columnar format library (`parquetjs`/Apache Arrow) or Athena client installed, and no network access to add one. Cold storage archives are NDJSON (the same substitute WO-047 already established for exports), not real Parquet. A real adapter is a drop-in later behind the same `COLD_STORAGE_ADAPTER` token: `uploadPartitionArchive` → S3 multipart upload + Parquet writer, `readArchive` → a ranged/streamed `getObject` (or an Athena query against the Parquet files), `deleteArchive` → `deleteObject`.

S3 lifecycle policy configuration (Standard → IA → Glacier transitions) is Terraform-only infrastructure with no real AWS account to apply it against in this sandbox — not implemented as code in this WO, consistent with every other "real cloud resource, no credentials" gap already documented across this codebase (KMS, S3 export storage, Kafka).

Kubernetes CronJob manifests for the two daily jobs were not authored as part of this WO: there is no live Kubernetes cluster in this sandbox to deploy or validate them against (same reasoning WO-048 applied to its own two scheduled jobs), and the shared `infrastructure/helm/base-service` chart has no existing CronJob template to extend safely without affecting every other service that chart deploys. Both jobs are implemented as directly-testable, real service classes (`ColdStorageTieringService.runDailyTiering()`, `RetentionPurgeService.runDailyPurge()`) that a CronJob would simply invoke on a schedule — the scheduling wrapper itself is a thin, untestable-in-this-sandbox layer around already-verified logic.

## A privilege-minimal exception for partition DDL

`ams_app` is never granted UPDATE/DELETE on `audit_events` (migration 005) and is never its owner, so it cannot run `ALTER TABLE ... DETACH PARTITION` / `DROP TABLE` directly. Migration 043 adds one `SECURITY DEFINER` function, `detach_and_drop_audit_events_partition(partition_name)`, that validates the partition name against the exact `audit_events_YYYY_MM` convention and confirms it is a genuine current partition before detaching+dropping it — running with the defining (migration-applying) role's privileges regardless of caller, but granting no ability to touch any live row, unlike granting `ams_app` ownership or blanket DDL rights would.

## A real concurrency bug found via testing: DETACH PARTITION vs. live traffic

`ALTER TABLE ... DETACH PARTITION` takes an `ACCESS EXCLUSIVE` lock on the parent table for the (brief) duration of the detach. Running the full backend suite (`npm test`, which runs many test files with real-Postgres integration tests concurrently) surfaced genuine deadlocks between this detach and unrelated concurrent tests' ordinary `audit_events` inserts (`TenantProvisioningSaga`'s own audit write). Confirmed via `git stash` that this exact deadlock class **pre-dates this WO** (it reproduces identically in unrelated OIDC/SAML/TOTP tests with none of this WO's code present) — it's a pre-existing property of running many parallel real-Postgres integration tests against one shared local instance, not a regression this WO introduced. This WO's own retention test file passes 100% reliably in isolation (multiple repeated runs), and only participates in the pre-existing flakiness class when run inside the full parallel suite.

Still, `ColdStorageTieringService`'s detach is a new source of a strong table-level lock, so it now protects itself with a short (`2s`) `lock_timeout` plus retry-with-backoff (up to 5 attempts) on `lock_not_available`/`deadlock_detected`/`serialization_failure` — giving concurrent live traffic priority instead of queuing indefinitely against it, the same defensive shape `AuditStoreRepository` already uses for its own hash-chain inserts. A real deployment should additionally schedule this job during a low-traffic window.

## Two real bugs found via testing

1. **Missing type cast on the `list_audit_events_partitions_older_than($1)` call** — `pg` sends an untyped parameter for a plain JS string/Date value, and Postgres couldn't resolve which overload to call (`function ... does not exist`). Fixed by explicitly casting: `($1::timestamptz)`.
2. **The DETACH/DROP-vs-live-traffic deadlock** described above — fixed with `lock_timeout` + retry, not just a retry (a bare retry on the query itself doesn't help when the OTHER session, not this one, is the deadlock victim that throws).
