# Next.js 16 Application Scaffold with Design System (WO-050)

## Reconciliation with WO-007's existing scaffold

WO-007 already delivered a **minimal** Next.js 16 (App Router) + React 19 scaffold at `frontend/`, explicitly described in its own `package.json` as proving "the build pipeline (Docker + strict TypeScript) works end to end" and deferring "the full design system, routing, and pages" to this work order. It already had: `output: "export"` (static export), TypeScript strict mode, a multi-stage Dockerfile (Node build → nginx-unprivileged runtime), and — via WO-009 — a real, working axe-core + Playwright accessibility scanner (`tests/accessibility/`) wired into CI (`.github/workflows/accessibility-scan.yml`).

None of ESLint, Prettier, Vitest, a Playwright *test-runner* config, husky-as-npm-package, lint-staged, or any UI/state dependency (shadcn/ui, Tailwind, Zustand, TanStack Query, zod, next-themes) existed yet — that was genuinely this WO's scope. Per this repo's established pattern (every later WO extends WO-007's scaffold in place — WO-008/009/011/012 all did this without re-scaffolding), this WO **extends** the existing `frontend/` package rather than regenerating it with `create-next-app`, which would have overwritten the Dockerfile, `next.config.js`, and the WO-009 accessibility harness.

## What changed structurally

- `app/` → `src/app/` (the AC calls for a `src/`-rooted feature-based layout with `@/*` → `./src/*` path aliases; WO-007's original layout had `app/` at the project root).
- New `src/components/ui/`, `src/features/`, `src/hooks/`, `src/stores/`, `src/lib/`, `src/types/`, `src/providers/`, `src/test/fixtures/` — the feature-based directories every subsequent frontend WO builds inside. `features/` and `hooks/` are empty except a README documenting the convention (no feature code exists yet — this WO is the scaffold, not the first feature).
- `tests/accessibility/discover-routes.ts` updated to look under `src/app` (a hardcoded path from WO-007/009's original `app/`-at-root layout).

## New tooling

- **Design system**: shadcn/ui conventions (`components.json`, `src/lib/utils.ts`'s `cn()` helper, `class-variance-authority`), Tailwind CSS v4 (CSS-first `@theme` config in `globals.css`, no `tailwind.config.ts` needed at this scale), one shadcn/ui component (`Button`) as the AC's verification baseline.
- **State**: `useAppStore` (Zustand) — typed `AuthContextState`, `ThemePreference`, `sidebarOpen`. `QueryProvider` (TanStack Query v5) — `staleTime: 30s`, `retry: 2`, `refetchOnWindowFocus: false` (an internal ops tool; explicit refresh/WebSocket is preferable to surprise background refetches). `ThemeProvider` (`next-themes`).
- **Env validation**: `src/env.ts`, a zod schema for `NEXT_PUBLIC_API_BASE_URL`/`NEXT_PUBLIC_WS_BASE_URL`/`NODE_ENV`, with **placeholder defaults** (`http://localhost:3001` / `ws://localhost:3001`) so `next build`'s static export keeps working without a real backend deployment configured — a real deployment overrides both via Docker `--build-arg` (see the Dockerfile's new `ARG`/`ENV` pair). `loadEnv()` is exported separately from the `env` singleton specifically so it's testable with both valid and invalid inputs without relying on module-load-time side effects.
- **Lint/format**: ESLint 9 flat config (`eslint.config.mjs`) using `eslint-config-next`'s native flat-config export (`eslint-config-next/core-web-vitals`) — **not** `FlatCompat`, which threw `TypeError: Converting circular structure to JSON` in this ESLint/eslint-config-next version combination (a real, reproducible bug found while wiring this up; the native flat-config export sidesteps it entirely). Layers the full `eslint-plugin-jsx-a11y` **strict** ruleset on top (the bundled config only carries 6 "recommended" rules), plus `typescript-eslint` strict rules (`no-explicit-any`, `no-floating-promises`, `consistent-type-imports`) and `eslint-config-prettier` to defer formatting to Prettier.
- **Prettier**: `.prettierrc.json` + `prettier-plugin-tailwindcss` (canonical class ordering).
- **Testing**: Vitest + jsdom + React Testing Library + `@testing-library/user-event`, 80% coverage thresholds (lines/functions/branches/statements) — barrel `index.ts` re-exports and `src/app/**` are excluded from coverage accounting (no logic of their own; `src/app` pages are covered by the Playwright/axe-core path instead). `next-themes`' `ThemeProvider` needs `window.matchMedia`, which jsdom doesn't implement — polyfilled in `src/test/setup.ts`.
- **E2E**: `playwright.config.ts` — a genuine Playwright *test-runner* config (distinct from WO-009's own raw-Playwright-API axe-core scanner script), serving the **built static export** (`npm run a11y:serve` → `out/`) rather than `next dev`, so a pass is evidence about the actual shipped artifact.
- **Pre-commit**: this repo has no root `package.json` and already has one repo-wide, optional bash pre-commit hook (`.husky/pre-commit`, activated via `git config core.hooksPath .husky`, real enforcement is CI per its own header comment) — introducing a second, npm-husky-managed hook here would fight over `core.hooksPath`. Instead, `.husky/pre-commit` now additionally runs `frontend`'s own `lint-staged` (`eslint --fix` + `prettier --write` on staged files) whenever a staged file lives under `frontend/`, keeping the existing hook as the single source of truth.

## A real bug found via testing: `serve`'s silent port fallback

`npm run a11y:serve` (`serve -l 4173 -s out`) silently falls back to a random port if 4173 is already in use, rather than erroring — this caused Playwright's E2E `webServer` (and, separately, the axe-core scan) to time out against a dead port with no obvious error pointing at the real cause. The actual issue during this WO's own verification was a stale `serve` process left over from an earlier manual test run still holding port 4173. Not a code fix (there's nothing in this repo's control over `serve`'s CLI behavior) — documented here as an operational gotcha: if `a11y:serve`/E2E ever times out mysteriously, check for a process already bound to 4173 first.

## What's still a placeholder

- `NEXT_PUBLIC_API_BASE_URL`/`WS_BASE_URL` point at `localhost:3001` — genuinely no deployed backend endpoint exists to point at yet; this is the AC's own "placeholders" language, not an oversight.
- `src/features/` has no real feature yet (only the directory-convention README) — the first real page/feature is subsequent-WO scope, matching this story's own framing ("every other frontend story depends on it").
- The Docker build stage was verified via `next build`/`npm run typecheck` locally, not via an actual `docker build` — no Docker daemon is available in this sandbox (the same documented gap as every backend WO's "no Docker/testcontainers" note). The Dockerfile's only change this WO made is two `ARG`/`ENV` lines for the new env vars; the existing multi-stage build/runtime structure (verified working by WO-007) is otherwise untouched.
- CI's `build-and-push.yml` pins Node 20 while the Dockerfile's build stage uses `node:24-alpine` — a version mismatch that predates this WO (WO-007's own choice); flagged, not fixed here, since it's out of this WO's stated scope and both versions satisfy Next.js 16/React 19's minimum requirements.
